## 2. Grill (ora-1 verdict)

### Q1: 3 vs 2 stores → **2 stores** (ora-1 wins over exp-1's 3)
- `isExecuting`/`resultData`/`error`/`lastSQL` change atomically in `executePivot` (orchestrator l:96-121)
- `pivot-view.tsx:56-60` reads all 3 result fields via one `useShallow` (one subscription either way)
- CONTEXT.md `PivotExecutionLifecycle` = one seam; execution+result = lifecycle state
- `isExecuting` is derived state of lifecycle (started→true, succeeded/error/aborted→false)
- 3 stores = over-split

**Final stores**:
- `usePivotConfigStore` (persisted) — `rows`/`columns`/`indicators`/`calculatedIndicators`/`filters`/`sort`/`totals` + add/remove/update/set actions + `loadConfig` + `getPivotConfig` + `reset`
- `usePivotExecutionStore` (ephemeral) — `isExecuting`/`resultData`/`error`/`lastSQL` + 4 setters + `reset()` + `clearResult()` (clears result fields only, preserves `isExecuting`)

### Q2: `reset()` → standalone `resetAllPivot()` in `pivot-facade.ts`
```ts
export function resetAllPivot() {
  usePivotConfigStore.getState().reset()
  usePivotExecutionStore.getState().reset()
}
```
Sole caller: `use-query-orchestrator.ts:60` (table change effect).

### Q3: `loadConfig(config)` → standalone `loadPivotConfig(config)` in `pivot-facade.ts`
```ts
export function loadPivotConfig(config: PivotConfig) {
  usePivotConfigStore.getState().loadConfig(config)
  usePivotExecutionStore.getState().clearResult()
}
```
`clearResult()` clears `resultData`/`error`/`lastSQL` but NOT `isExecuting` (preserves current behavior — l:205-217 doesn't clear isExecuting). Sole caller: `useHistorySelect` in `pivot-config.tsx`.

### Q4: `addCalculatedIndicator` validation → config action calls `usePivotExecutionStore.getState().setError()`
Unidirectional config→execution dependency. No circular import (execution store doesn't import config store). `error` stays in execution store (displayed at `pivot-view.tsx:120` — already subscribes to execution store).

### Q5: `getPivotConfig()` — pure config, moves to config store. No change.

### Q6: Persistence — only config store gets `persist` + `partialize` + `merge: migratePivotPersisted`. Execution store is plain `create()`. **Keep persistence key `"pivot-store"`** (same shape, loads existing dev state cleanly).

### Q7: Migration — direct, no wrapper. 4 consumers, mechanical changes.

### Q8: Phase ordering — P1 (create, additive) → P2 (atomic migrate + rename + strip) → P3 (update tests). Writer+reader must migrate together (orchestrator writes to execution store, readers read from execution store — can't split writer from reader).
